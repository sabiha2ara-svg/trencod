Security & backend: implemented behavior

This is a source-based description, not an independent security audit or a guarantee about a particular deployment.

  • Database: Python/Flask backend uses PostgreSQL when DATABASE_URL is configured; local development uses SQLite. On Render startup fails without DATABASE_URL instead of silently storing data on temporary disk. Connection failures do not fall back to SQLite.
  • Authentication: passwords use salted PBKDF2-SHA256 (600,000 iterations); older scrypt hashes are upgraded after login. Random session tokens are stored hashed in the database. Session cookies use HttpOnly and SameSite; Secure depends on HTTPS public URL configuration.
  • Storage: projects, shared artwork, revisions, purchase records and supported music clips are stored in the database. File limits apply. Server backups and restore testing remain the owner's responsibility; this update does not recover deleted data.
  • Permissions: server routes check project ownership and Studio membership. Shared saves check revisions. Purchases update coins, ownership and receipts in a transaction; competing buyers cannot both acquire the same exclusive listing.
  • Execution: HTML/JS previews use sandboxed iframes with scripts enabled and without same-origin permission. Python practice uses Pyodide in a browser worker, with timeout and Stop controls. Uploaded game code is not run as server-side Python.
  • Limits: iframe sandboxing is not complete network isolation or a CPU/memory quota. Games may contact external services, and JavaScript can freeze a tab. Do not enter passwords into games. Python packages require external downloads. There has been no independent penetration test.
  • Request protection: JSON writes, Origin/host checks, parameterized SQL, authentication and rate limits cover supported routes. These controls are not a claim of comprehensive protection.

Report vulnerabilities through the private security category above. Do not post exploit details in team chat. Account recovery and independent audit are not promised features.

Report a vulnerability

Use private feedback and choose Security. Explain affected features without including passwords, API keys or database URLs. Do not test other users’ accounts or publicly post exploit details. Reports require login; there is no separate account-recovery channel configured by this release.
